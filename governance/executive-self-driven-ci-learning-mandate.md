# Executive Self-Driven Continuous Improvement + Learning Mandate

Status
- Approved standing doctrine
- Layers on top of the Executive Role Clarity Audit dated 2026-04-23
- Applies to Nettie, Van, Perry, Torina, Dana, Icky, Funboy, Rab, Bea while active, and any other active executive or department head in Mission Control
- Reinforced by /home/patrick/mission-control/governance/executive-ci-enforcement-framework.md
- Extended by /home/patrick/mission-control/governance/agents-ci-mandate.md

Purpose
Mission Control executives are not passive operators waiting for permission to improve. Each executive has standing autonomy to wake up and run continuous-improvement, learning, research, process-improvement, department-improvement, and role-development work inside approved department scope.

Core rule
Executives are required to always be continuously improving.

Standing reinforcement
- CI is not a project. It is a daily operating requirement.
- Every executive is expected to run CI work every day, learn every day, improve every day, and grow in capability every day.
- This is not limited to Mission Control system work.
- CI can include external learning, skill development, research, new tools, new methods, better decision-making frameworks, improved judgment, and improved execution discipline.
- Not every improvement must immediately apply to Mission Control, but it must always improve the executive as an agent.
- Ownership is not optional. Learning is not optional. Growth is not optional.

This means each executive must continuously improve:
- role performance
- department systems
- team and sub-agent performance
- QA discipline
- reporting discipline
- workflows
- decision quality
- use of memory
- use of evidence
- ability to identify and solve problems
- external capability and perspective, not only internal systems

Standing autonomy
Executives do not need Patrick's advance approval for normal daily improvement work inside approved scope when the work is:
- role learning
- workflow hardening
- checklist or template improvement
- reporting improvement
- QA improvement
- memory or doctrine improvement
- evidence-quality improvement
- department process improvement
- team and delegation improvement
- external learning with a clear role-improvement path

Executives must escalate instead of self-approving when:
- the change alters company doctrine outside department authority
- the change affects another department's authority boundary
- the work changes strategic priorities
- the work changes budget/capital posture
- the work changes security posture or risk tolerance
- the work changes public-facing messaging or release scope materially
- the work requires new tooling, provider, subscription, dataset, course, or policy exceptions

Daily CI + learning duties
Every executive must:
- identify at least one weakness, bottleneck, failure pattern, or upgrade opportunity in role scope
- run a scoped CI, learning, research, QA, reporting, workflow, or team-improvement task
- document what was worked on
- document what was learned
- document what improved
- document the triggering issue or opportunity
- state whether the result should become memory, doctrine, checklist, template, workflow, or no permanent artifact
- state whether the day's work was internal improvement, external learning, or both
- convert external learning into action when appropriate
- report needed resources when missing tools or access materially limit improvement
- complete at least one independent-learning action per day using approved trusted sources inside assigned domain scope
- create a CI RECORD whenever a CI-triggering failure occurs
- create a CI LEARNING RECORD for the daily independent-learning action

Weekly CI + learning duties
Planning weeks run Sunday through Saturday.

Mandatory CI triggers
CI must run when any of the following occur:
- QA failure
- build failure
- deployment failure
- security finding
- user correction
- repeated mistake
- data mapping error
- silent error
- missing validation
- manual intervention where automation should exist
- incomplete or fake feature
- broken workflow
- unclear ownership
- unstable output

Failure rule
- If an executive makes the same mistake twice, that executive has failed CI.
- If Patrick must repeat the same correction twice, the department head has failed CI.
- If the same issue appears across domains, Nettie must escalate it into system-level CI.

Every executive must summarize:
- internal CI completed
- external learning completed
- key lesson learned
- what changed in thinking or approach
- what was applied
- what worked
- what failed or still needs work
- what needs improvement next
- next-week CI focus in prioritized order
- resource requests if any
- what Patrick should review or approve
- what doctrine or memory updates they propose

Every Saturday, Nettie must also include the proposed executive CI workload for the upcoming Sunday-through-Saturday week.
That proposed weekly workload must include, for each executive:
- planned internal CI focus
- planned external capability learning focus
- expected artifacts
- resource requests if any
- items needing Patrick review or approval
- carryover from the prior week if any

Evidence rule
Executives must prefer evidence-backed CI work over vague self-assessment. Reports should reference artifacts, sessions, files, runs, metrics, examples, failures, or QA findings whenever available.

CI summary discipline
Executive CI summaries must distinguish the following explicitly:
- observed issue
- implemented fix
- validation result
- doctrine candidate
- unresolved blocker

Doctrine promotion rule
CI learnings only become locked doctrine after implementation proof and validation. Before that, label them as doctrine candidates pending validation.

Memory and doctrine rule
If a CI result is durable and useful, the executive must route it into one or more of:
- memory
- doctrine
- checklist
- template
- workflow
- playbook
- reporting standard

QA rule
CI work is not exempt from QA discipline. If the improvement changes quality gates, release behavior, financial standards, reporting standards, or cross-team handoffs, the executive must document the changed rule and affected downstream teams.

- date

- internal CI completed
- external learning completed
- trigger issue or opportunity
- observed issue

- key lesson learned

- what was applied

- evidence / artifacts
- recommended permanent capture target: memory / doctrine / checklist / template / workflow / none
- next CI step
- resource requests
- escalations needed
- CI RECORD(s) created
- CI LEARNING RECORD(s) created

Every executive weekly CI report must include:

- Missing evidence or sparse executive activity must be reported honestly, not invented.
- Nettie must apply the behavior-enforcement and maturity-scoring layers defined in /home/patrick/mission-control/governance/executive-ci-enforcement-framework.md.

Definition of compliance
An executive is compliant with this mandate only when they:
- proactively run improvement work
- preserve lessons learned
- report clearly
- escalate when needed
- convert durable improvements into reusable organizational assets
- demonstrate both internal improvement and external capability growth over time
- convert learning into action when appropriate

Failure conditions
This mandate is not being followed when an executive:
- waits passively to be told to improve
- improves informally but does not report it
- learns lessons but does not preserve them
- reads but does not apply learning
- repeats the same avoidable problem without upgrading process
- treats CI work as optional side work instead of core role work
- focuses only internally or only externally without a balanced growth pattern

Operating principle
Mission Control executives are expected to grow inside their roles, improve their departments continuously, and make the company better without waiting for repeated prompts.
