# Department Head Operational Memory Standard

## Purpose
Define the minimum persistent operating structure required for any Mission Control department head to function as a real operational owner instead of a decorative persona.

## Minimum required files

### 1. IDENTITY.md
Must include:
- title
- purpose
- authority
- reporting path
- primary users served
- decision limits

### 2. DOMAIN_OWNERSHIP.md
Must include:
- owned domains
- shared domains
- forbidden domains
- escalation triggers
- required collaborators

### 3. MEMORY.md
Must include:
- active context
- persistent doctrine
- recurring decisions
- live project lessons
- known user preferences
- current constraints
- examples of successful completion

### 4. TASKS.md
Must include:
- active tasks
- blocked tasks
- pending review items
- recurring responsibilities
- completion criteria

### 5. rules.md
Must include:
- operating rules
- refusal/rejection conditions
- quality standards
- safety/compliance constraints
- escalation rules

### 6. handoffs.md
Must include:
- inbound handoff format
- outbound handoff format
- QA handoff format
- Nettie summary format
- Hermes execution packet format when relevant

### 7. RUNBOOKS
Each department head must have runbooks for routine responsibilities.
Every runbook must include:
- purpose
- trigger
- prerequisites
- step-by-step process
- required artifacts
- stop conditions
- QA checks
- handoff requirements

## Enforcement doctrine
- A department head is not production-ready if any required file is missing or functionally empty.
- Empty placeholder memory is not operational memory.
- Generic completion criteria without domain-specific steps do not count as runbook coverage.
- Nettie must not assume a department head knows a procedure that is not written in persistent files.
- Hermes must reject execution packets that depend on unwritten procedure memory when corrective documentation has not been created.
- Perry/QA may reject outputs that do not identify governing runbooks, required artifacts, verification evidence, and risks.

## Minimum autonomy test
A department head is only considered autonomous when they can:
1. receive a correctly scoped handoff
2. identify the governing runbook
3. execute the routine process without Patrick supplying step-by-step instructions
4. produce required artifacts on disk
5. hand off to QA or Nettie in a decision-useful format
6. escalate only genuine missing inputs or authority conflicts

## Review cadence
- audit all department heads whenever new roles are added
- re-audit after major doctrine changes
- re-audit after repeated execution failures caused by missing procedure memory
